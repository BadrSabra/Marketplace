أنت الآن مسؤول عن تطوير صفحة العميل بعد تسجيل الدخول في مشروع Mit Gaber Hyperlocal Marketplace.

الهدف النهائي:
- إعادة تصميم صفحة ما بعد تسجيل دخول العميل لتكون مستوحاة من مزيج بين Noon وAmazon وAlibaba.
- تحسين تجربة التصفح، البحث، عرض المتاجر، عرض المنتجات، والعروض.
- الحفاظ على البنية الحالية إن كانت جيدة، وعدم كسر أي وظائف موجودة.
- العمل بأسلوب: استكشاف → توثيق → تنفيذ → اختبار → تقرير.

مهم جدًا:
- لا تبدأ أي تعديل قبل إنهاء الاستكشاف الكامل.
- لا تفترض وجود مكونات أو endpoints غير موجودة.
- إذا وجدت مكونات أو صفحات جاهزة، أعد استخدامها بدل إعادة بنائها من الصفر.
- أي تغيير يجب أن يكون مبنيًا على ما هو موجود فعلًا في المشروع.

==================================================
المرحلة 1: الاستكشاف الكامل لما هو موجود
==================================================

أولًا، افحص بنية المشروع المتعلقة بصفحة العميل بعد تسجيل الدخول:

1) ابحث عن الصفحات والمسارات المرتبطة بالعميل:
- صفحة ما بعد تسجيل الدخول
- الصفحة الرئيسية للعميل
- صفحة المنتجات
- صفحة المتاجر
- صفحة البحث
- صفحة السلة إن وجدت
- أي layout أو shell مخصص للعميل

2) افحص المكونات الحالية:
- Header
- Search bar
- Hero banner / carousel
- Product cards
- Store cards
- Category section
- Footer
- Loading states
- Empty states
- Error states

3) افحص طبقة البيانات:
- ما هي endpoints المستخدمة للمنتجات؟
- ما هي endpoints المستخدمة للمتاجر؟
- هل يوجد endpoint للبحث؟
- هل يوجد endpoint للعروض أو المنتجات المميزة؟
- هل يوجد caching via TanStack Query أو غيره؟
- ما هي queryKeys المستخدمة؟
- ما هي أسماء الحقول الفعلية في البيانات المسترجعة؟

4) افحص الهوية المرئية الحالية:
- الألوان
- الخطوط
- اتجاه الصفحة RTL/LTR
- وجود تعريب أو عدمه
- وجود تصميم متجاوب للموبايل

5) افحص سلوك الصفحة الحالي:
- ماذا يظهر للمستخدم بعد تسجيل الدخول؟
- هل الصفحة تعرض متاجر؟
- هل تعرض منتجات؟
- هل يوجد بحث؟
- هل يوجد فلترة؟
- هل توجد بانرات أو أقسام مقترحة؟
- هل توجد مشاكل في التحميل أو routing أو البيانات؟

6) سجّل تقرير استكشاف منظم يحتوي على:
- الملفات الموجودة
- الملفات المفقودة
- المكونات الموجودة
- المكونات الناقصة
- endpoints الموجودة
- endpoints المطلوبة
- queryKeys الموجودة
- queryKeys الناقصة
- المشاكل المرئية الحالية
- أي ملاحظات عن UX أو الأداء أو البنية

مخرج المرحلة 1 يجب أن يكون واضحًا جدًا، ومقسمًا إلى:
- موجود بالفعل
- ناقص
- يحتاج تحسين
- خطر/مشكلة محتملة

==================================================
المرحلة 2: وضع خطة تنفيذ مبنية على الاستكشاف
==================================================

بعد الاستكشاف، ضع خطة تنفيذ دقيقة تشمل:

1) هيكل الصفحة المقترح:
- Header علوي واضح
- Search bar قوي وسريع
- Hero section / promotional banner
- قسم تصنيفات
- قسم المنتجات المميزة
- قسم المتاجر المحلية
- قسم عروض اليوم
- Footer

2) نمط التصميم المطلوب:
- مستوحى من Noon: بساطة، وضوح، بانرات، عناوين قوية
- مستوحى من Amazon: كثافة معلومات مفيدة، بطاقات واضحة، توصيات
- مستوحى من Alibaba: إبراز المتاجر والبائعين والمنتجات بشكل تجاري
- النتيجة النهائية يجب أن تكون مزيجًا متوازنًا، لا نسخة مطابقة لأي منصة

3) الأولويات:
- البحث أولًا
- عرض المنتجات ثانياً
- عرض المتاجر ثالثاً
- تحسين تجربة التصفح والتنقل
- تحسين حالات التحميل والفراغ والأخطاء
- الحفاظ على سرعة الصفحة

4) قرار reuse vs rebuild:
- إذا كان هناك مكون جيد موجود، أعِد استخدامه
- إذا كان المكون معقدًا وغير مناسب، عدّله بدل استبداله
- ابنِ مكونات جديدة فقط عند الحاجة

==================================================
المرحلة 3: التنفيذ
==================================================

نفّذ التغييرات تدريجيًا وبترتيب واضح:

1) Header
- شعار المنصة
- Search bar رئيسي
- أيقونة الحساب
- أيقونة السلة
- أيقونة الإشعارات إن كانت موجودة
- دعم RTL بشكل كامل

2) Search experience
- بحث عن المنتجات والمتاجر
- autocomplete إن كان ممكناً باستخدام البيانات الموجودة
- fallback عند عدم توفر autocomplete
- عرض نتائج البحث بشكل واضح وسريع

3) Hero banner
- استخدم banner أو carousel إذا كانت هناك صور/بيانات جاهزة
- إن لم توجد صور جاهزة، أنشئ layout placeholder احترافي
- يمكن استخدام رسائل ترويجية عامة إلى حين توفر محتوى حقيقي
- يجب أن يكون responsive

4) Product sections
- قسم للمنتجات المميزة
- قسم للمنتجات الجديدة
- قسم حسب الفئة
- كل بطاقة منتج يجب أن تحتوي:
  - صورة
  - الاسم
  - السعر
  - حالة التوفر
  - اسم المتجر إن كان مناسبًا
  - زر إضافة للسلة أو عرض التفاصيل إن كان موجودًا

5) Store sections
- عرض المتاجر المحلية بطريقة جذابة
- لكل متجر:
  - شعار أو صورة
  - الاسم
  - الوصف المختصر
  - التقييم إن وجد
  - عدد المنتجات أو مؤشرات عامة إن وجدت
- اجعل القسم واضحًا ومناسبًا للتصفح السريع

6) Category navigation
- أضف قسم تصنيفات واضح
- اربط التصنيفات بالمنتجات إن كانت البيانات متوفرة
- استخدم chips أو cards حسب ما يناسب التصميم الحالي

7) Loading / empty / error states
- loading skeletons
- empty state مفيد بدل فراغ الصفحة
- error state واضح وقابل للفهم
- لا تجعل الصفحة تبدو مكسورة إذا تأخر API

8) RTL & localization
- تأكد أن الصفحة تعمل بشكل صحيح بالعربية
- ضبط direction
- محاذاة النصوص
- المسافات والهوامش
- الأسهم والاتجاهات في الواجهات التفاعلية

9) Performance
- lazy loading للصور
- تجنب إعادة rendering غير ضرورية
- استخدم cache بشكل صحيح
- لا تكرر الطلبات بلا سبب

==================================================
المرحلة 4: الاختبارات
==================================================

بعد التنفيذ، شغّل اختبارات شاملة تغطي ما يلي:

A) اختبارات البيانات
- هل يتم جلب المنتجات بنجاح؟
- هل يتم جلب المتاجر بنجاح؟
- هل البحث يعمل؟
- هل التصنيفات تعرض البيانات الصحيحة؟
- هل queryKeys صحيحة؟
- هل cache invalidation يعمل؟

B) اختبارات الواجهة
- هل الـ Header يظهر بشكل صحيح؟
- هل شريط البحث يعمل؟
- هل البانر يظهر؟
- هل بطاقات المنتجات تظهر؟
- هل بطاقات المتاجر تظهر؟
- هل الصفحة تبدو جيدة على الموبايل والسطح المكتب؟
- هل RTL يعمل كما يجب؟

C) اختبارات الحالات الخاصة
- حالة عدم وجود منتجات
- حالة عدم وجود متاجر
- حالة فشل API
- حالة تأخر التحميل
- حالة بيانات ناقصة مثل صورة مفقودة أو سعر مفقود

D) اختبارات التنقل
- هل روابط التفاصيل تعمل؟
- هل الانتقال بين الأقسام يعمل؟
- هل زر السلة أو الحساب يعمل إذا كان موجودًا؟
- هل الرجوع من الصفحات الداخلية يعمل؟

E) اختبارات التوافق مع الأدوار
- تأكد أن الصفحة مناسبة للعميل فقط
- لا تكسر صلاحيات Store Owner أو Driver أو Admin
- لا تغيّر routes الخاصة بالأدوار الأخرى

F) اختبارات تلقائية أو شبه تلقائية
- إن أمكن، أضف أو حدّث tests للـ components أو hooks
- إن لم توجد tests، اكتب smoke test plan واضح
- نفّذ فحصًا يدويًا/آليًا لكل سيناريو رئيسي

==================================================
المرحلة 5: تقرير النتائج
==================================================

في النهاية، قدّم تقريرًا نهائيًا مفصلًا يحتوي على:

1) ما كان موجودًا قبل التعديل
2) ما الذي تم تعديله
3) ما الذي تم إضافته
4) ما الذي لم يتم تغييره ولماذا
5) نتائج الاختبارات
6) أي مشاكل متبقية
7) توصيات للمرحلة التالية

صيغة التقرير يجب أن تكون منسقة، ويفضل أن تشمل JSON مختصرًا مثل:

{
  "discovery": {
    "existingFiles": [],
    "existingComponents": [],
    "existingEndpoints": [],
    "gaps": []
  },
  "implementation": {
    "header": "done",
    "search": "done",
    "heroBanner": "done",
    "productsSection": "done",
    "storesSection": "done",
    "rtl": "done",
    "performance": "done"
  },
  "tests": {
    "dataFetch": "pass",
    "uiRendering": "pass",
    "responsive": "pass",
    "emptyStates": "pass",
    "errors": "pass",
    "navigation": "pass",
    "roleSafety": "pass"
  },
  "notes": [],
  "nextSteps": []
}

==================================================
قواعد مهمة جدًا
==================================================

- لا تفترض أن أي endpoint موجود قبل التحقق.
- لا تفترض أن أي component قابل لإعادة الاستخدام قبل فحصه.
- لا تغيّر أي route أو role protection إلا إذا كانت جزءًا من الصفحة الجديدة فعلًا.
- لا تكسر أي شيء موجود.
- لا تبدأ في التنفيذ قبل اكتمال الاستكشاف.
- إذا وجدت نقصًا في البيانات، عالج الواجهة بحل مؤقت أنيق بدل إظهار أخطاء للمستخدم.
- اجعل التجربة النهائية أقرب لواجهة marketplace احترافية، سريعة، وواضحة.
