# 12 — Change Management Policy
**سياسة إدارة التغيير**

---

## المبدأ الأساسي

> **"كل تغيير لم يُحلَّل أثره هو دين تقني مؤجل."**  
> لا تغيير يدخل المنتج دون مرور بالعملية.

---

## 1. دورة حياة الطلب (RFC Lifecycle)

```
طلب جديد (Feature Request / Bug / Tech Debt)
    ↓
TRIAGE (تصنيف أولي — 24 ساعة)
    ↓
ANALYSIS (تحليل أثر — 1-3 أيام)
    ↓
ESTIMATION (تقدير الجهد — يوم)
    ↓
PRIORITIZATION (ترتيب الأولوية — في Sprint Planning)
    ↓
READY (معايير DoR محققة)
    ↓
IN DEVELOPMENT
    ↓
REVIEW + TESTING
    ↓
DEPLOYED
    ↓
MONITORED (30 دقيقة بعد deployment)
    ↓
CLOSED
```

## 3. تحليل الأثر (Impact Analysis)

```markdown
## Impact Analysis Template

**الميزة:** [اسمها]
**المحلل:** [الاسم]
**التاريخ:** [التاريخ]

### الأثر التقني
- الملفات التي ستتغير: [قائمة]
- تغييرات DB Schema: [ نعم / لا ] → Migration مطلوبة؟
- تغييرات API: [ Breaking / Non-breaking / جديدة ]
- تأثير على ميزات أخرى: [اذكرها]
- تأثير على الأداء: [تقدير]

### الأثر الأمني
- هل تتعامل مع بيانات حساسة؟
- هل تُضيف صلاحية جديدة؟
- هل تُضيف upload أو external call؟

### الأثر على المستخدمين
- هل تُغيِّر behavior موجود يعتمد عليه المستخدمون؟
- هل تتطلب migration للبيانات الموجودة؟
- هل تتطلب تواصلاً مع المستخدمين؟

### التعقيد والجهد
- الحجم: [ XS / S / M / L / XL ]
- الوقت المقدّر: [ساعات أو أيام]
- المخاطر: [اذكرها]
- Dependencies: [ما الذي يجب أن يكتمل أولاً؟]
```

## 4. تقدير الوقت

```
نموذج التقدير الثلاثي (لتقليل التحيز):

Optimistic (كل شيء يسير مثالياً): X ساعات
Realistic (التوقع المعقول):        Y ساعات
Pessimistic (حدث الأسوأ):         Z ساعات

التقدير النهائي = (O + 4R + P) / 6

مثال:
  Optimistic: 4h
  Realistic: 8h
  Pessimistic: 16h
  النهائي: (4 + 32 + 16) / 6 ≈ 8.7h → نقول 9h

أضف دائماً 20% buffer للـ integration والاختبار.
```

## 5. تقدير المخاطر

| المخاطرة | الاحتمال | الأثر | الأولوية |
|---------|---------|-------|---------|
| تغيير في المالية | عالٍ | عالٍ | 🔴 Critical |
| تغيير في Auth | متوسط | عالٍ | 🟠 High |
| تغيير DB Schema | عالٍ | متوسط | 🟠 High |
| API Breaking Change | متوسط | متوسط | 🟡 Medium |
| UI Change | منخفض | منخفض | 🟢 Low |

## 6. ترتيب الأولويات (Prioritization Framework)

```
نستخدم RICE Score:
  R = Reach (كم مستخدم يتأثر، 1-10)
  I = Impact (مدى التأثير، 1-3: Massive=3, High=2, Medium=1)
  C = Confidence (مدى ثقتنا بالتقدير، 100%-20%)
  E = Effort (الجهد بالأسابيع)

RICE = (R × I × C) / E

مثال:
  Cloud Storage: (8 × 3 × 100%) / 0.75 weeks = 32
  Google Maps:   (5 × 2 × 80%) / 0.5 weeks  = 16
  Dark Mode:     (3 × 1 × 90%) / 0.25 weeks = 10.8

يُنجَز الأعلى RICE Score أولاً.
```

## 7. منع Scope Creep

```
تعريف Scope Creep: إضافة متطلبات جديدة لمهمة جارية دون تقدير جديد

أعراضه:
  "بينما أنت هنا، أضف أيضاً..."
  "صغيرة، تأخذ 5 دقائق"
  "هذا طبيعي يُضاف معها"

الحكم:
  ✅ إذا كانت مرتبطة مباشرة بالـ Acceptance Criteria → ممكن
  ✅ إذا كانت تمنع تسليم الـ Story → ممكن
  ❌ إذا كانت إضافة مستقلة → Story جديدة في الـ Backlog

الردّ القياسي:
"هذا فكرة ممتازة. سأسجلها كـ Story منفصلة لكي نُقدِّرها ونُخطط لها بشكل صحيح."
```

---

## 8. رفض التغييرات غير المناسبة

```
يُرفض الطلب إذا:
  ❌ يتعارض مع Architecture Principles
  ❌ يكسر backward compatibility بدون مبرر واضح
  ❌ ليس له business value واضح
  ❌ مخاطره تفوق فوائده
  ❌ dependencies غير مكتملة
  ❌ يُدخل تقنية جديدة بدون اختبار كافٍ

صياغة الرفض:
"شكراً لهذا الطلب. نرفضه حالياً لأن [السبب].
إذا تغير [الشرط]، يمكن إعادة النظر في [الوقت]."
```

